# 概述

线上接口突然不可用，CPU/内存不高，但出现大量 `CLOSE_WAIT`。通过 jstack + 线程分析工具定位到连接池耗尽，再用 C3P0 未归还连接调试开关找到 Hibernate Session 未关闭的代码点并修复。

| 项 | 说明 |
| --- | --- |
| 现象 | 接口异常 + 大量 CLOSE_WAIT；堆栈卡在等待 DataSource |
| 根因 | 定时任务里 `openSession()` 后未在 finally 关闭，连接泄漏占满池 |
| 适用边界 | C3P0 + Hibernate；池子偏小、定时任务高频探活时更易暴露 |
| 不适用 | HikariCP 等其它池需换对应泄漏诊断手段 |

# 环境与前置

| 项 | 说明 |
| --- | --- |
| 连接池 | C3P0 |
| ORM | Hibernate |
| 诊断 | `jstack`；IBM Thread and Monitor Dump Analyzer for Java（或同类工具） |

> 文中 JDBC URL / 账号均为**脱敏示例**，请勿照抄生产口令。

# 现象

- 业务接口超时或失败  
- 主机 CPU、内存并不高  
- 网络侧可见大量 `CLOSE_WAIT`

# 分析过程

## 1. 抓取线程栈

故障窗口执行 `jstack <pid>`，用线程分析工具查看阻塞点：调用链停在等待 DataSource 可用连接。

## 2. 核对 C3P0 配置（关键参数）

```properties
# 示例（已脱敏）
jdbc.driverClassName=com.mysql.jdbc.Driver
jdbc.url=jdbc:mysql://<db-host>:3306/<db_name>?useUnicode=true&characterEncoding=utf-8&autoReconnect=true
jdbc.username=<user>
jdbc.password=********

c3p0.acquireIncrement=1
c3p0.initialPoolSize=5
c3p0.minPoolSize=5
c3p0.maxPoolSize=5
c3p0.maxIdleTime=60
c3p0.testConnectionOnCheckout=false
c3p0.preferredTestQuery=SELECT 1
# 排查泄漏时临时打开：
# c3p0.unreturnedConnectionTimeout=100
# c3p0.debugUnreturnedConnectionStackTraces=true
```

| 参数 | 本文故障值 | 含义 |
| --- | --- | --- |
| `maxPoolSize` | **5** | 池上限；泄漏数达到上限即拖垮接口 |
| `minPoolSize` / `initialPoolSize` | 5 | 启动即占满下限 |

> 原文曾误写「最大连接 20」；以配置文件中的 `maxPoolSize=5` 为准。池越小，泄漏越快被放大。

## 3. 打开未归还连接调试

开启 `unreturnedConnectionTimeout` 与 `debugUnreturnedConnectionStackTraces` 后重启，日志打印逾期 checkout 栈，指向：

`DalScheduleJob.isDbOnline()` → Hibernate `Session` / `Criteria` 查询。

## 4. 代码：修复前 vs 修复后

**修复前（泄漏）：** `openSession()` 后无关闭，或 finally 缺失。

**修复后：**

```java
public boolean isDbOnline() {
    Session session = null;
    try {
        session = sessionFactory.openSession();
        Criteria criteria = session.createCriteria(Asset.class);
        criteria.add(Restrictions.eq("resourceCode", 10008L));
        criteria.uniqueResult();
        return true;
    } catch (Exception e) {
        logger.error("刷新缓存前检测数据库连接出错", e);
        return false;
    } finally {
        if (session != null) {
            session.close();
        }
    }
}
```

调小池子并压测定时任务路径可快速复现；修复后 CLOSE_WAIT 与排队等待消失。

# 验证清单

| 检查项 | 期望 |
| --- | --- |
| 接口 | 持续访问正常 |
| 连接池 | 活跃连接不再顶满 `maxPoolSize` |
| 调试开关 | 生产确认稳定后关闭 `debugUnreturnedConnectionStackTraces`（有开销） |
| CLOSE_WAIT | 不再堆积 |

# 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 堆栈等 DataSource | 池耗尽 | 查泄漏或临时扩容；根治仍是还连接 |
| 有 try/catch 仍泄漏 | 关闭写在 catch 或遗漏 finally | 统一 finally / try-with-resources |
| 调试无栈 | 超时阈值过大或未重启 | 调小 `unreturnedConnectionTimeout` 并重启 |

# 小结

1. **CLOSE_WAIT + 等连接** 优先怀疑池耗尽与连接泄漏，而不是先加机器。  
2. C3P0 的未归还连接调试能直接打到业务栈，比盲翻代码快。  
3. Hibernate `Session` 必须在 finally 关闭；池参数描述必须与配置文件一致。
