Docker 基于 Tomcat 镜像部署 JavaWeb 应用程序

发表于 2026-09-22 更新于 2026-09-23 分类于 Docker 本文字数： 3.2k 阅读时长 ≈ 12 分钟

前言

把 Java Web 部署到服务器上，通常要先安装 JDK 和 Tomcat，并核对版本与路径。换一台机器就要重做，环境稍有差别，项目就启动失败。容器把 JDK 和 Tomcat 封进镜像：构建一次，在装有 Docker 的机器上用同一镜像启动，不再依赖宿主机是否已经装好 Java。

本文用 Ridgeyard 走完官方 Tomcat 镜像部署。测试时把 WAR 挂进容器；生产时编写 Dockerfile，放入解压后的 ROOT，再用 Docker Swarm 发布。按文中命令可以完成打包、构建、启动、访问和排错。

环境依赖与版本说明

本文命令在 Ubuntu 22.04、linux/amd64 上执行通过。Windows、macOS 安装 Docker Desktop 后，使用相同的 docker 命令；CentOS 7 已停止维护，不作为本次 Engine 版本的验证系统。

核心原理简述

官方 Tomcat 镜像里已经带有 JDK 和 Tomcat 进程。容器启动后执行 catalina.sh run，宿主机不必再安装 Java。

标准 Java Web 的部署逻辑是：把 WAR 放到镜像内的 /usr/local/tomcat/webapps/。文件名决定上下文，ROOT.war 对应网站根路径 /，app.war 对应 /app。Tomcat 启动时会解压 WAR。

Ridgeyard 的生产镜像不走 “启动后再解压”。Maven 先产出目录 target/ROOT，构建时拷进 webapps/ROOT。这样 jdbc、Redis 等配置可以按单个文件挂到 WEB-INF/classes，不会在解压时被盖掉，也不会把整个 config 目录盖住 Spring 的 XML。

两种用法：

方式适用做法
挂载部署无外部配置的临时验证docker run 把 WAR 挂进官方镜像
自定义镜像生产Dockerfile 打入应用，配置挂载，Swarm 发布

端口映射把容器 8080 接到宿主机端口。Swarm 使用 mode: host 时，这个端口只出现在正在跑副本的那台节点上。数据挂载把宿主机文件映进容器，改配置不用重新构建镜像。

flowchart TB
    mvn["mvn package 得到 target/ROOT"] --> copy["同步到构建目录 war/ROOT"]
    copy --> image["docker build 打入 Tomcat 镜像"]
    image --> stack["docker stack deploy"]
    cfg["宿主机配置文件"] --> stack
    stack --> wait["等待 MySQL、Redis、Elasticsearch 端口"]
    wait --> tomcat["catalina.sh run"]

规划目录

堆栈文件里的 ./Ridgeyard/... 相对于执行 docker stack deploy 时的 docker/ 目录。

宿主机（相对 docker/）容器内
Ridgeyard/war/ROOT/usr/local/tomcat/webapps/ROOT（构建时打进镜像）
Ridgeyard/config 下各个 propertiesWEB-INF/classes/config/ 中的同名文件
Ridgeyard/conf/log4j.propertiesWEB-INF/classes/conf/log4j.properties
Ridgeyard/tomcat/conf/server.xml/usr/local/tomcat/conf/server.xml

口令只写在宿主机 properties 中。jdbc、Redis、Elasticsearch 的主机使用 overlay 服务名和容器端口。当前环境没有消息队列时，rabbitmq.enabled、amqp.enabled、rocketmq.enabled 保持 0。

编写 Dockerfile

在 docker/Ridgeyard 下构建。下面与当前镜像一致：补齐健康检查和 ifconfig，拷入已解压的 ROOT，启动前等待依赖端口。

指令作用
FROM锁定 Tomcat 9.0 与 JDK 8，避免 latest 漂移
RUN apt-get安装 curl、ifconfig 等，并删掉 apt 缓存以减小层体积
COPY war/ROOT应用进入镜像；构建上下文必须是 docker/Ridgeyard
EXPOSE 8080声明容器端口，真正发布由堆栈的 ports 完成
CMD/wait 读环境变量 WAIT_HOSTS，通过后执行 catalina.sh run

/wait 来自开源工具 docker-compose-wait 2.12.1。它在应用启动前检查 WAIT_HOSTS 里的 主机:端口 是否可连接，超时由 WAIT_TIMEOUT 控制。镜像构建前，读者自行下载 Linux x86-64 的可执行文件，放到构建上下文中：

现象原因处理
打开 / 是 404，或不是登录页上下文不是根路径，或应访问 /login.doWAR 命名为 ROOT.war，或使用已解压的 webapps/ROOT；地址加上 /login.do
管理节点的 8080 连不上，堆栈却显示已部署host 模式端口只在任务节点docker stack ps 看 NODE，访问该节点 IP
容器启动后马上退出，日志里找不到 ifconfig许可程序调用 ifconfig，基础镜像默认没有使用带 net-tools 和 /usr/bin/ifconfig 链接的 Dockerfile 重新构建
日志停在等待依赖WAIT_HOSTS 的服务名或端口不通，180 秒超时在同一 overlay 上检查 3306、6379、9200
进程起来但数据源报错整目录挂载盖住了 Spring XML，或 JDBC 仍指向容器外地址改回按文件挂载；jdbc.url 使用 <mysql-service>:3306
健康检查一直 unhealthystart_period 只有 10 秒，Tomcat 尚未监听加大 start_period 后 docker service update；确认镜像里有 curl
宿主机端口绑定失败8080 已被占用`ss -lntp
挂载后应用读不到配置宿主机文件权限不足，或路径不是 docker/ 下的相对路径保证运行用户可读；在 docker/ 目录执行 stack deploy

总结与拓展

生产路径可以收成四步：mvn -DskipTests package，sh docker/copy.sh，在 docker/Ridgeyard 构建并推送镜像，在 docker/ 执行 docker stack deploy。访问地址使用任务节点上的 http://<任务节点IP>:8080/login.do。配置变更用 docker service update --force，不要把口令写进 Dockerfile。

方面传统安装 JDK 与 Tomcat本文的容器部署
环境每台机器单独安装、单独对齐版本JDK 8 与 Tomcat 9.0.122 在镜像中固定
迁移重装运行时并拷贝应用拉取同一镜像，挂上配置后启动
配置散落在服务器目录宿主机文件挂载，与镜像分层
发布手工替换 WAR构建镜像后由 Swarm 滚动任务

镜像推到私有仓库后，任务节点只需能拉取该标签。继续扩展时，可在构建流水线里执行打包和 docker build，发布阶段只更新服务镜像。当前副本保持 1，端口使用 host 模式，因此扩容前要先规划每台节点的端口和调度标签。

完成发布后，可持续观察 docker stack ps <stack-name> 是否保持 Running，以及 docker service logs -f <stack-name>_ridgeyard 里依赖等待和 Tomcat 启动是否连续成功。
