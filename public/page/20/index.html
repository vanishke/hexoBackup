概述

线上接口突然不可用，CPU / 内存不高，但出现大量 CLOSE_WAIT。通过 jstack + 线程分析工具定位到连接池耗尽，再用 C3P0 未归还连接调试开关找到 Hibernate Session 未关闭的代码点并修复。

项说明
现象接口异常 + 大量 CLOSE_WAIT；堆栈卡在等待 DataSource
根因定时任务里 openSession() 后未在 finally 关闭，连接泄漏占满池
适用边界C3P0 + Hibernate；池子偏小、定时任务高频探活时更易暴露
不适用HikariCP 等其它池需换对应泄漏诊断手段

环境与前置

项说明
连接池C3P0
ORMHibernate
诊断jstack；IBM Thread and Monitor Dump Analyzer for Java（或同类工具）

文中 JDBC URL / 账号均为脱敏示例，请勿照抄生产口令。

现象

  • 业务接口超时或失败
  • 主机 CPU、内存并不高
  • 网络侧可见大量 CLOSE_WAIT

分析过程

1. 抓取线程栈

故障窗口执行 jstack <pid>，用线程分析工具查看阻塞点：调用链停在等待 DataSource 可用连接。



2. 核对 C3P0 配置（关键参数）

参数本文故障值含义
maxPoolSize5池上限；泄漏数达到上限即拖垮接口
minPoolSize / initialPoolSize5启动即占满下限

原文曾误写「最大连接 20」；以配置文件中的 maxPoolSize=5 为准。池越小，泄漏越快被放大。

3. 打开未归还连接调试

开启 unreturnedConnectionTimeout 与 debugUnreturnedConnectionStackTraces 后重启，日志打印逾期 checkout 栈，指向：

DalScheduleJob.isDbOnline() → Hibernate Session / Criteria 查询。

4. 代码：修复前 vs 修复后

修复前（泄漏）： openSession() 后无关闭，或 finally 缺失。

修复后：

调小池子并压测定时任务路径可快速复现；修复后 CLOSE_WAIT 与排队等待消失。

验证清单

检查项期望
接口持续访问正常
连接池活跃连接不再顶满 maxPoolSize
调试开关生产确认稳定后关闭 debugUnreturnedConnectionStackTraces（有开销）
CLOSE_WAIT不再堆积

常见问题

现象原因处理
堆栈等 DataSource池耗尽查泄漏或临时扩容；根治仍是还连接
有 try/catch 仍泄漏关闭写在 catch 或遗漏 finally统一 finally / try-with-resources
调试无栈超时阈值过大或未重启调小 unreturnedConnectionTimeout 并重启

小结

  1. CLOSE_WAIT + 等连接 优先怀疑池耗尽与连接泄漏，而不是先加机器。
  2. C3P0 的未归还连接调试能直接打到业务栈，比盲翻代码快。
  3. Hibernate Session 必须在 finally 关闭；池参数描述必须与配置文件一致。

MySQL 数据丢失原因

概述

用 mysqldump 导出的 SQL 导入本地时，若脚本里带有 DROP DATABASE，而你只改了后面的库名却没改 DROP 目标，就可能把源库名对应的库删掉。本文还原一次真实踩坑的因果链，并给出安全导入清单。

项说明
现象导入「改名后的库」时，原始库被删除
根因--add-drop-database 生成了 DROP DATABASE IF EXISTS \原库名 `；改名只改了CREATE DATABASE`，未改 DROP
适用边界MySQL / MariaDB；mysqldump --databases + --add-drop-database 场景
不适用仅表级 dump（无 DATABASE 语句）、或导入前已手工剔除 DROP 的脚本

环境与前置

  • 导出端具备对应库读权限
  • 导入端账号具备 DROP / CREATE 权限（这也是风险来源）
  • 操作前确认：导入目标是否允许执行 DROP DATABASE

现象复现要点

导出片段常见形态：

若导入前只把 CREATE DATABASE / USE 改成了 iepg_xw，却留下：

则导入时会先删掉 iepg，再创建 iepg_xw——于是表现为「改名导入却把原库干掉了」。

原理要点

1. 真正的风险语句是 DROP DATABASE

--add-drop-database 的设计意图是：导入同名库前先清掉旧库，保证幂等。它不会自动跟着你手工改过的新库名走。

2. /*! ... */ 不是「普通注释」

MySQL 条件注释形如：

对支持该版本特性的 MySQL 服务端，其中的语句会被执行。把它贴进客户端执行「居然成功」并不奇怪——它本来就不是被忽略的备注。

因此：看到 /*!40000 DROP DATABASE ...*/ 必须按可执行 DDL 对待，不能当文档注释跳过。

安全导入清单

  1. 导入前全文搜索：DROP DATABASE / DROP SCHEMA，确认目标库名是否符合预期。
  2. 改名导入时同步改三处：DROP DATABASE、CREATE DATABASE、USE。
  3. 更稳妥：导出时去掉 --add-drop-database；或导入前删除全部 DROP DATABASE 行。
  4. 权限收敛：导入账号尽量无 DROP 库级权限（开发机另议）。
  5. 先干跑：在临时实例导入；或对脚本做 grep -n "DROP DATABASE" 人工复核。
  6. 生产库禁止直接拿「改过库名的 dump」盲导。

验证清单

检查项期望
导入前 SHOW DATABASES记录原有库列表
脚本扫描无意外 DROP DATABASE
导入后目标库存在；不应消失的库仍在
表数量 / 抽样数据与导出端一致

常见问题

现象原因处理
只想换库名却删了旧库DROP 仍指向旧名同步修改或删除 DROP 行
以为 /*! */ 不会执行误判为普通注释按可执行 SQL 审核
本地误删无法恢复无备份从导出源或备份集恢复；建立导入前快照习惯

小结

  1. 丢数据的直接原因是 DROP DATABASE，不是「注释语法好奇」本身。
  2. --add-drop-database 与「手工改库名」组合时，必须把 DROP 目标一并改对或去掉。
  3. 条件注释 /*! ... */ 在 MySQL 中可执行——审核 dump 时按 DDL 风险等级处理。
