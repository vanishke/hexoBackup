通过 jdk 工具 keyTool 生成证书

生成证书命令

导出证书命令

keyTool 命令参数

-genkey 在用户主目录中创建一个默认文件”.keystore”, 还会产生一个 mykey 的别名，mykey 中包含用户的公钥、私钥和证书
(在没有指定生成位置的情况下, keystore 会存在用户系统默认目录，如：对于 window xp 系统，会生成在系统的 C:/Documents and Settings/UserName/文件名为 “.keystore”)
-alias 产生别名
-keystore 指定密钥库的名称 (产生的各类信息将不在.keystore 文件中)
-keyalg 指定密钥的算法 (如 RSA DSA（如果不指定默认采用 DSA）)
-validity 指定创建的证书有效期多少天
-keysize 指定密钥长度
-storepass 指定密钥库的密码 (获取 keystore 信息所需的密码)
-keypass 指定别名条目的密码 (私钥的密码)
-dname 指定证书拥有者信息 例如： “CN = 名字与姓氏, OU = 组织单位名称, O = 组织名称, L = 城市或区域名称, ST = 州或省份名称, C = 单位的两字母国家代码”
-list 显示密钥库中的证书信息 keytool -list -v -keystore 指定 keystore -storepass 密码
-v 显示密钥库中的证书详细信息
-export 将别名指定的证书导出到文件 keytool -export -alias 需要导出的别名 -keystore 指定 keystore -file 指定导出的证书位置及证书名称 -storepass 密码
-file 参数指定导出到文件的文件名
-delete 删除密钥库中某条目 keytool -delete -alias 指定需删除的别 -keystore 指定 keystore -storepass 密码
-printcert 查看导出的证书信息 keytool -printcert -file yushan.crt
-keypasswd 修改密钥库中指定条目口令 keytool -keypasswd -alias 需修改的别名 -keypass 旧密码 -new 新密码 -storepass keystore 密码 -keystore sage
-storepasswd 修改 keystore 口令 keytool -storepasswd -keystore e:/yushan.keystore(需修改口令的 keystore) -storepass 123456 (原始密码) -new yushan (新密码)
-import 将已签名数字证书导入密钥库 keytool -import -alias 指定导入条目的别名 -keystore 指定 keystore -file 需导入的证书

C3p0 连接池泄漏分析

发表于 2022-05-27 更新于 2026-09-23 分类于 MySQL 本文字数： 731 阅读时长 ≈ 3 分钟

概述

线上接口突然不可用，CPU / 内存不高，但出现大量 CLOSE_WAIT。通过 jstack + 线程分析工具定位到连接池耗尽，再用 C3P0 未归还连接调试开关找到 Hibernate Session 未关闭的代码点并修复。

项说明
现象接口异常 + 大量 CLOSE_WAIT；堆栈卡在等待 DataSource
根因定时任务里 openSession() 后未在 finally 关闭，连接泄漏占满池
适用边界C3P0 + Hibernate；池子偏小、定时任务高频探活时更易暴露
不适用HikariCP 等其它池需换对应泄漏诊断手段

环境与前置

项说明
连接池C3P0
ORMHibernate
诊断jstack；IBM Thread and Monitor Dump Analyzer for Java（或同类工具）

现象

  • 业务接口超时或失败
  • 主机 CPU、内存并不高
  • 网络侧可见大量 CLOSE_WAIT

分析过程

1. 抓取线程栈

故障窗口执行 jstack <pid>，用线程分析工具查看阻塞点：调用链停在等待 DataSource 可用连接。



2. 核对 C3P0 配置（关键参数）

参数本文故障值含义
maxPoolSize5池上限；泄漏数达到上限即拖垮接口
minPoolSize / initialPoolSize5启动即占满下限

原文曾误写「最大连接 20」；以配置文件中的 maxPoolSize=5 为准。池越小，泄漏越快被放大。

3. 打开未归还连接调试

开启 unreturnedConnectionTimeout 与 debugUnreturnedConnectionStackTraces 后重启，日志打印逾期 checkout 栈，指向：

DalScheduleJob.isDbOnline() → Hibernate Session / Criteria 查询。

4. 代码：修复前 vs 修复后

修复前（泄漏）： openSession() 后无关闭，或 finally 缺失。

修复后：

调小池子并压测定时任务路径可快速复现；修复后 CLOSE_WAIT 与排队等待消失。

验证清单

检查项期望
接口持续访问正常
连接池活跃连接不再顶满 maxPoolSize
调试开关生产确认稳定后关闭 debugUnreturnedConnectionStackTraces（有开销）
CLOSE_WAIT不再堆积

常见问题

现象原因处理
堆栈等 DataSource池耗尽查泄漏或临时扩容；根治仍是还连接
有 try/catch 仍泄漏关闭写在 catch 或遗漏 finally统一 finally / try-with-resources
调试无栈超时阈值过大或未重启调小 unreturnedConnectionTimeout 并重启

小结

  1. CLOSE_WAIT + 等连接 优先怀疑池耗尽与连接泄漏，而不是先加机器。
  2. C3P0 的未归还连接调试能直接打到业务栈，比盲翻代码快。
  3. Hibernate Session 必须在 finally 关闭；池参数描述必须与配置文件一致。
